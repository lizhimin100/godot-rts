## 流场寻路系统（v1 初版）

### 架构

- **FlowField.gd**：`RefCounted` 纯算法类，无 Godot 节点依赖，可多实例化
  - `grid[][]`：0=可通行, 1=障碍（树木/建筑）
  - 8方向 BFS（含对角线，代价 1.0/1.414）
  - Dijkstra 松弛传播（遇更短距离则更新）
  - 方向场：每格指向代价最低邻居
- **流场寻路.gd**：`static` 适配器，持 FlowField 实例
  - TileMap 转 grid 二维数组
  - 世界坐标 ↔ 网格坐标转换
  - 缓存管理（目标不变不重算，障碍变更标记 dirty）
  - `local_update()` 已实现但未接入（v1 限制）

### 调用链路

```
用户右键点击
  → 命令移动(目标)
    → 移动基类._触发流场计算()    ← 只在新目标时重建
    → _physics_process
      → _导航移动到()
        → 流场寻路.获取方向(pos, fallback)  ← 每帧
        → velocity = 方向 × 速度
        → velocity.move_toward(加速度)     ← 速度平滑
        → move_and_slide()
```

### 外部接口

| 调用方 | 方法 |
|--------|------|
| 建筑放置管理器 | `流场寻路.初始化()`, `流场寻路.刷新障碍()` |
| 移动基类 | `流场寻路.计算流场(目标)`, `流场寻路.获取方向(pos, fallback)` |
| 城堡.gd | `流场寻路.是障碍(pos)` |
| 农民.gd | `流场寻路.刷新障碍()` |

## 渲染排序（Z 轴体系）

### 核心机制：y_sort_enabled

`场景/平面.tscn` 中，`单位` 节点开启了 `y_sort_enabled = true`，其所有子节点按 Y 轴位置升序渲染（Y 越大越靠前，即屏幕下方的单位覆盖上方的单位）。

### 深度排序规则

| 层 | 渲染顺序 | 机制 |
|----|---------|------|
| 地面 | 最底层 | TileMapLayer，场景树最前面 |
| 树木 | 地面之上，始终在单位下方 | 与"单位"同层，但出现在场景树更前位置 |
| 单位/建筑 | 按 Y 递增渲染 | `y_sort_enabled = true` |
| 战争迷雾 | 覆盖层 | `z_index = 2` |
| UI | 最上层 | CanvasLayer |

### y_sort_origin

- **建筑**（`建筑基类.gd:34`）：`y_sort_origin = 碰撞高度/2`，从建筑底部排序
- **单位**（`移动基类.gd:67`）：`y_sort_origin = 碰撞高度/2`，从脚底排序
- 树木不参与 y_sort（TileMapLayer 整层渲染），始终位于单位下方

## UI 设计体系

### 设计原则来源

参考了两个 Godot UI 教程的核心方法论：

**① 「Godot 4 主题编辑器制作漂亮 UI」（16BitDev / BV11efiYaEuh）**
- 用 Theme 资源统一全局控件样式，而非在每个节点上手写 overrides
- StyleBoxTexture + 九宫格（9-Slice）纹理实现可伸缩面板
- 字体、颜色、间距统一在一个主题文件中管理

**② 「Godot UI 基础 — 构建在任何地方都适用的漂亮界面」（BV1K84y1X7Yc）**
- 容器嵌套替代手动定位：用 HBoxContainer / VBoxContainer / MarginContainer 构建层级
- Size Flags（Fill + Expand）实现弹性布局，锚点（Anchor）做全局定位
- NinePatchRect 做面板背景，TextureButton 做互动按钮

### UI 架构

```
全屏 → CanvasLayer（HUD层）
    ├── 顶栏资源条（PanelContainer > MarginContainer > HBoxContainer × 3组）
    ├── 右侧按钮面板（VBoxContainer，anchor_right）
    ├── 小地图（SubViewportContainer，右上）
    └── UI提示框位置（Control，居中锚点）

覆盖层 → CanvasLayer（营地覆盖层）
    ├── 暗色背景（ColorRect，全屏，alpha=0.65）
    └── 返回按钮（右上角）
```

## Godot 4.7 技术坑记录

### .tscn 中 Color 必须用 4 参数 RGBA
- **现象**：Godot 4.7 在加载 `.tscn` 文件时，若 `Color` 值使用 3 参数（如 `Color(1, 1, 1)`），会报 "Parse error" 且无法加载场景。
- **原因**：Godot 4.7 的文本格式解析器 `resource_format_text.cpp` 在解析节点属性时，要求 `Color` 必须显式提供全部 4 个分量 (R, G, B, A)。3 参数写法虽然在 GDScript 运行时是合法的（会自动补 A=1.0），但在 .tscn 文本解析阶段不被接受。
- **影响范围**：所有 `.tscn` / `.tres` 文件中 Label 的 `theme_override_colors/font_color` 以及其他 Color 属性。
- **修复方法**：`Color(1, 1, 1)` → `Color(1, 1, 1, 1)`
- **预防措施**：在 `.tscn` 文件中写 `Color` 时始终使用 4 参数；在 GDScript 中写 `Color` 可以使用 3 参数（运行时会正确补全 alpha）。
