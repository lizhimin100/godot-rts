# Phase 2 Migration Report — 首单位迁移验证

> 生成日期：2026-07-05
> 迁移单位：**剑士**（Swordsman）
> 迁移标志：`_using_movement_solver = true`

---

## 1. 迁移对象

| 属性 | 值 |
|------|-----|
| 类名 | `剑士` (extends `单位基类`) |
| 文件 | `单位/剑士/剑士.gd` |
| 场景 | `单位/剑士/剑士.tscn` |
| 主场景实例 | 3（剑士×1, 剑士2, 剑士3 in `场景/平面.tscn`） |
| 移动速度 | 250 px/s（UnitStats 中最快） |
| 战斗类型 | 近战（melee，无投射物） |
| 内部状态机 | ✅ `单元状态机` |
| 自定义 velocity 写入 | 无 |
| 对运动服务实例的直接引用 | 无 |
| `_using_movement_solver` | `true`（唯一迁移单位） |

### 选择理由

在所有单位类型中，剑士是**架构复杂度最低**的：

```
剑士     → 纯 UnitBase + 单元状态机，无 velocity 写入
弓箭手   → 同上 + 投射物（需额外验证动画时序）
农民     → 双重状态机 + 直接引用运动服务 + 建造瞬移
人族步兵 → 混合旧状态机 + 直接写 velocity（必须先重构）
人族农民 → 同上
主角控制器 → 独立 CharacterBody2D（非 UnitBase 体系）
敌人.gd   → 独立 CharacterBody2D（非 UnitBase 体系）
```

## 2. 迁移修改

### 2.1 剑士.gd — 唯一修改

在 `_ready()` 中 `super._ready()` 之后添加一行：

```gdscript
# ⭐ Movement 2.0 Phase 2: 迁移到 MovementSolver
_using_movement_solver = true
```

**零架构修改**：不修改 MovementIntent、MovementSolver、状态机、队形系统、避障系统、流场系统。

### 2.2 代码路径激活

| 组件 | 迁移前 | 迁移后 |
|------|--------|--------|
| `剑士._ready()` | 无变化 | `_using_movement_solver = true` |
| `UnitBase.立即停止()` | 调 `运动服务.强制停止()` | 清除 intent + 调 `MovementSolver.强制停止()` |
| `状态机._发出移动请求()` | 调 `应用移动请求()` | 写 `MovementIntent`（不走旧路径） |
| `状态机._发出追击请求()` | 调 `应用移动请求()` | 写 `MovementIntent` |
| `状态机._发出移动攻击请求()` | 调 `应用移动请求()` | 写 `MovementIntent` |
| `状态机._重发移动请求()` | 旧停止+发请求 | 新清意图+写意图 |
| `运动服务.请求移动()` | 正常处理 | **gate跳过**（`_using_movement_solver=true`） |
| `运动服务.强制停止()` | 正常处理 | **gate跳过**（重定向到 MovementSolver） |
| `运动服务._更新所有移动单位()` | 正常处理 | **gate跳过**剑士 |
| `MovementSolver._physics_process` | 无单位处理 | **处理剑士**的 MovementIntent |

## 3. 功能验证（代码路径分析）

### 3.1 MoveTo（右键移动）

```
用户右键点击地面
  → 命令管理器.发出命令(type=MOVE, pos)
  → 剑士.设置命令(MOVE, pos)
  → 状态机.立即响应()
  → _决定下一状态() → 状态.移动
  → _入场动作(移动) → _发出移动请求()
  → MovementIntent.move_to(目标位置)
  → 剑士.移动意图 = intent
  → [下一帧 _physics_process]
  → MovementSolver (priority 0, autoload):
    → 读取 剑士.移动意图 (type=MOVE_TO)
    → _意图转请求 → 前往位置移动 策略
    → 策略.计算速度() → 流场方向 × 移动速度
    → 三力合成（路径+队形×0.6+分离×0.4）
    → ★ 剑士.velocity = 最终速度
  → UnitBase._physics_process (scene node priority 0):
    → move_and_slide()
  ✓ 链路完整
```

**无障碍**：命令对象大小写正确、意图类型枚举匹配、策略类名匹配。

### 3.2 到达检测

```
MovementSolver._解析单位():
  → 策略.是否已到达() → true
  → data.已到达 = true
  → 剑士.velocity = Vector2.ZERO
  → _发送结果(已到达) → 发射 移动完成 信号
  → [同步触发]
  → 状态机._on_移动完成() → _on_到达()
  → 剑士.当前命令 = 命令类型.无
  → [下一帧] 状态机.当前状态 → 待机
  ✓ 链路完整
```

**行为差异**：旧系统中运动服务(priority -100)发射信号→状态机(priority -1)同帧切换。新系统中状态机(-1)先跑→MovementSolver(0)后发射信号→状态机**下一帧**才切换。动画过渡延迟 1 帧（~16ms），物理行为一致。

### 3.3 卡死恢复

```
MovementSolver._检测卡死():
  → 期望 > 阈值 且 实际 < 阈值 持续 0.5s
  → 回退阶段：反向移动 0.3 秒
  → 卡死计数++，若 >= 3 放弃
  → 放弃时 velocity=0, 发射 移动完成(STUCK)
  → 状态机._on_卡死() → 保留命令
  ✓ 逻辑与旧系统完全一致（代码逐字复制）
```

### 3.4 队形移动

```
多选剑士，右键移动:
  → 命令管理器.创建队形(方阵, 间距48)
  → 设 _pending_formation_offset / slot
  → 状态机._发出移动请求():
    → MovementIntent.formation_offset = offset
    → MovementIntent.formation_slot = slot
  → MovementSolver:
    → _意图转请求 → 队形数据写入 移动请求
    → 前往位置移动 策略: 读取队形槽位
    → 队形系统.计算队形力() × 0.6
    → MOVING_TO_SLOT → SLOT_LOCKED 锚点回归
  ✓ 链路完整
```

### 3.5 追击（右键敌人）

```
右键敌人:
  → 命令管理器.发出命令(type=ATTACK, target=敌人)
  → 状态机._决定攻击状态():
    → 距离 > 攻击范围 → 状态.追击
  → _发出追击请求():
    → MovementIntent.pursue(敌人)
  → MovementSolver:
    → 追击目标移动 策略
    → 每帧重采样目标位置
    → 进入攻击范围 → 策略返回到达
    → 状态机 → 攻击状态
  ✓ 链路完整
```

### 3.6 移动攻击（A-move）

```
A + 右键:
  → 命令管理器.命令攻击移动()
  → 状态机 → 移动攻击
  → MovementIntent.attack_move(位置)
  → MovementSolver:
    → 移动攻击移动 策略
    → 沿途策略._索敌() → 发现敌人返回 ZERO
    → 攻击结束后继续移动
  ✓ 链路完整
```

## 4. 发现的问题

### 4.1 已知差异：到达信号时序

| 系统 | 到达信号帧 | 状态切换帧 | 动画过渡 |
|------|-----------|-----------|----------|
| 旧（运动服务 -100） | 帧 N | 帧 N（同帧） | 同帧切换 |
| 新（MovementSolver 0） | 帧 N | 帧 N+1 | 延迟 1 帧 |

**影响**：到达后的动画过渡（移动→待机）延迟 1 帧。物理行为（停止位置、速度归零）无差异。

**缓解方案**：当前 MovementSolver 在到达时已直接调用 `unit._切换动画("待机")`（L239），所以动画切换是在 MovementSolver 自己发射信号时同步发生的。实际上动画切换与信号发射同帧，**不存在实际延迟**！回顾代码：

```gdscript
# MovementSolver.gd:233-239
data.已到达 = true
unit.velocity = Vector2.ZERO
_发送结果(unit, 移动结果.结果类型.已到达)
if unit.has_method("_切换动画"):
    unit._切换动画("待机")  # ← 同帧切换！
```

✅ **动画同步**：MovementSolver 在写入 velocity=0 的同帧调用 `_切换动画("待机")`，与旧系统行为一致。

**实际差异概率**：**极低**。仅状态机的 `当前状态` 变量延迟 1 帧更新（从"移动"变为"待机"），但这仅影响外部通过 `单元状态机.当前状态` 查询状态的代码（如剑士 flip_h 判断中的 `_状态机.当前状态 == 单元状态机.状态.攻击` 路径）。剑士的动画由 `_切换动画` 直接驱动，不受状态机延迟影响。

### 4.2 已知差异：状态机即时响应

`UnitBase.设置命令()` 中的 `_状态机.立即响应()` 同步运行，会在 MovementSolver 之前在同一帧内切换意图。这意味着中断命令（新右键覆盖旧移动）**零帧延迟**。

**验证**: 在 `状态机.立即响应()` → `_发出移动请求()` → 写新意图，MovementSolver 在 priority 0 读到最新意图。已验证。

### 4.3 安全问题：双信号源

剑士迁移后：
- 状态机连接了**两个**信号源（运动服务 + MovementSolver）
- 运动服务的 gate 会跳过剑士 → 不会发射信号
- MovementSolver 正常发射信号 → 状态机正常处理
- `_on_移动完成` 中 `if 移动单位 != _单位: return` 防重复

✅ **安全**：不会收到重复信号。

### 4.4 运动服务残余数据安全

剑士迁移前（训练时）可能已通过 `应用移动请求()` 在运动服务注册。迁移后：
- `_using_movement_solver = true` 后，状态机不再调 `应用移动请求()`
- 但 `UnitBase.立即停止()` 仍会调 `运动服务.强制停止()`（旧路径清理）
- 运动服务的 gate 在 `强制停止()` 中检测到 `_using_movement_solver` 并跳过

⚠️ **极端情况**：剑士在迁移前发出移动请求但未完成，然后迁移标记被设置。旧 `_移动中单位` 中的残留数据会被运动服务的 `_更新所有移动单位` gate 移除（`待移除.append(单位); continue`）。

✅ **安全**：有清理路径。

## 5. MovementSolver 与旧运动服务差异对比

| 维度 | 运动服务（旧） | MovementSolver（新） |
|------|--------------|---------------------|
| velocity 写入 | `单位.velocity = 最终速度` | `unit.velocity = 最终速度` |
| 三力合成 | `路径+队形×0.6+分离×0.4` | 完全相同 |
| 到达检测 | `策略.是否已到达()` | 完全相同 |
| SLOT_LOCKED | 内联在 `_移动中单位` 字典 | 内联在 `_单位数据` 字典 |
| 卡死检测 | `_检测卡死()` | 逐字复制的 `_检测卡死()` |
| 策略构建 | `_构建策略(请求)` | 自己的 `_构建策略(intent)` |
| 空间哈希 | 自己构建 | **复用运动服务的哈希** |
| 信号 | `移动完成(单位, 结果)` | 相同格式 |
| 性能模型 | 批次处理所有单位 | 迭代器过滤，只处理已迁移 |
| 策略实例 | 每次请求新建 | **缓存 per-unit**（意图类型不变复用） |
| 处理顺序 | priority -100 | priority 0（autoload vs scene） |

**核心差异**：MovementSolver 缓存策略实例，减少每帧对象创建。这不是行为差异而是优化。

## 6. 是否可以迁移下一批单位

### 6.1 弓箭手 — ✅ 可迁移

**理由**：
- 与剑士架构完全一致（纯 UnitBase + 单元状态机）
- 无 velocity 写入
- 无运动服务实例引用
- 额外工作量：验证投射物（箭矢）在 MovementSolver 写入 velocity 后正确生成

**修改**：弓箭手.gd `_ready()` 中添加 `_using_movement_solver = true`

### 6.2 农民 — ⚠️ 需先解决

**阻塞问题**：
1. `_physics_process` 中直接引用 `运动服务.实例.是否在移动(self)`（建造到达检测）
2. `_physics_process` 中直接引用 `运动服务.实例.是否是槽锁定(self)`（动画管理）
3. 建造使用 `应用移动请求(移动请求.技能驱动(...))`（不走状态机意图路径）

**解决方案**：为这些检查添加 MovementSolver 等效接口，或让农民同时读取两个系统的状态。

### 6.3 人族步兵/人族农民 — ❌ 不可迁移

**阻塞问题**：
- 使用旧手动状态机（不是 `单元状态机`）
- 直接在 `_physics_process` 中写 `velocity`
- 依赖 `UnitController.compute_velocity()`（旧系统）

**前提条件**：必须先重写这些单位为纯 UnitBase + 单元状态机构架。
